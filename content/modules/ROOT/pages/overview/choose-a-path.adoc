The start page introduced three ways to run OpenClaw: the recipe's raw manifests, claw-installer, and an OpenShell sandbox.
All three end with an OpenClaw gateway you can chat with, but they get there by different routes.
So which one is yours?
Let's line them up on the questions that usually decide it: who gets in, which image runs, where the configuration lives, what happens on an upgrade, who needs cluster-admin rights, and how far along each path is.
If you only want the short answer, the recipe recommends the raw manifests.
The rest of the page shows you when one of the others might still fit better, and which limits come with every choice.

== Who gets in

This is the row where the three paths differ the most, so let's start here.

With the raw manifests, the gateway token in the Secret `openclaw-secrets` is the key to the front door.
Through a port-forward, the token is all you need, because OpenClaw approves the pairing of a local browser by itself.
A browser that comes through the Route isn't a local connection, so OpenClaw also wants to approve it as a device.
You approve it by its request ID with the OpenClaw CLI in the Pod.
The Route makes the login screen reachable for anyone who can reach the cluster's router.
The token and the device approval are what keep everyone else out.
xref:admin/access.adoc[Open the Control UI] walks you through both ways in.

claw-installer puts a second door in front of the first one.
Its OpenShift plugin adds an OAuth proxy sidecar, binds the gateway to loopback, and points the Route at the proxy, so a browser that opens the Control UI signs in with an OpenShift account first.
The proxy leaves the `/metrics` and `/api` paths unauthenticated, though.
Here's the catch, though.
The proxy asks only for the `user:info` scope, which lets in any authenticated OpenShift user, not just the members of your project.
Limiting it to your project takes a different proxy setting plus a ClusterRoleBinding for `system:auth-delegator`, and creating that binding needs cluster-admin.
After the OpenShift login, OpenClaw still asks for the gateway token and a device approval.
The installer's *Instances* tab helps with both: *Open* fills in the token for you, and *Approve Pairing* approves the waiting browser.

The sandbox turns all of this around.
The recipe starts the gateway inside the sandbox with `--bind loopback --auth none`, so it listens only inside the sandbox and asks for no token at all.
You reach it with `openshell forward start`, which brings port 18789 to your own machine.
It's a setup for trying things out, and that's how the recipe describes this path, too.

== Which image runs

The raw manifests pin the OpenClaw image by digest, for the init container and the gateway alike.
You run OpenClaw {openclaw-version}, the version the recipe was tested with, until you change the digest yourself.

claw-installer's default gateway image is `ghcr.io/openclaw/openclaw:latest`, and its init container always uses `registry.access.redhat.com/ubi9-minimal:latest`.
If you pick the installer's OpenShell sandbox backend, the default gateway image becomes `quay.io/sallyom/openclaw-openshell:latest` instead.
Unlike a digest, none of these tags pins a particular build.
The form's *Image* field replaces the default gateway image, so that's where a pinned reference goes if you want one.

For the sandbox, you build the image yourself from the recipe's `Containerfile.openshell`.
It pins OpenClaw {openclaw-version} and a Node.js release whose download it checks against a checksum, but it starts `FROM quay.io/hmoghani/openshell-base:latest`.
The starter kits publish that base image for development and testing, so the pinning stops one layer short.
xref:developer/build-image.adoc[Build and push the images] covers building the images, including the base.

== Where the configuration lives

With the raw manifests, the ConfigMap only seeds the first start.
After that, OpenClaw owns its copy of `openclaw.json` on the PVC, and you change a running gateway with `config patch`.
xref:overview/architecture.adoc#configuration-the-secret-the-configmap-and-a-one-time-copy[How the deployment fits together] explains why it works that way.

claw-installer does the opposite.
Its init container copies `openclaw.json` from the ConfigMap onto the PVC on every start.
That's the very behavior the recipe's troubleshooting guide blames for settings that revert after a restart in older versions of its manifests.
With the installer, you change deploy-level settings by deploying again from the form, and the installer replaces the resources it manages.

Inside the sandbox, the recipe starts the gateway with `--allow-unconfigured` and gives it no model configuration at all.
xref:developer/sandbox-model-config.adoc[Configure the model inside the sandbox] picks up where the recipe stops.

== What happens on an upgrade

Upgrades are where the gateway's start command suddenly matters.
The OpenClaw image's entrypoint runs `openclaw doctor --fix` before it starts a foreground gateway, and doctor is what migrates your state to the new version.
The raw manifests keep that entrypoint in place, so doctor runs before every new image takes over.
The architecture page walks through the mechanism in xref:overview/architecture.adoc#why-the-gateway-starts-through-args[Why the gateway starts through `args`].

claw-installer replaces the gateway container's command with its own shell command, unless you tick *Use image entrypoint* in the form.
With the command replaced, the image's entrypoint never runs, and neither does doctor.
OpenClaw's Docker documentation is clear about that case: if you replace the entrypoint, run doctor against the same state yourself before you start the gateway.
The installer's docs reserve *Use image entrypoint* for images that need their own startup script, so on an installer deployment, that doctor run is your job.

In the sandbox, the OpenClaw version is a build argument of the image.
A new version means a new image, and the recipe doesn't describe how to move an existing sandbox onto it.

== Who needs cluster-admin

The recipe's README promises a deployment with "no cluster-admin required".
For the raw manifests themselves, that holds, and namespace-scoped access is all you need.
Two optional pieces need more, though.

MLflow tracing on RHOAI 3.3.1::
The tracing overlay binds the `mlflow-integration` ClusterRole to its ServiceAccount, and RHOAI 3.3.1 doesn't ship that role.
You create it from the definition in the starter kits' shared MLflow guide.
A ClusterRole is a cluster-scoped object, so creating one takes cluster-wide RBAC rights, the kind of change that claw-installer's docs leave to a cluster administrator.
xref:admin/tracing.adoc[Send traces to MLflow] has the details.

OpenShell::
Before the OpenShell Helm chart goes in, the cluster needs the Agent Sandbox controller and its cluster-scoped CRDs, and the chart neither installs nor upgrades them.
claw-installer's README, which comes with an OpenShell setup of its own, files the OpenShell installation under cluster-admin work as well.
So the administrator comes back for OpenShell upgrades, too.
xref:admin/install-openshell.adoc[Install OpenShell for sandboxes] covers the installation.
After that, developers create their sandboxes through the `openshell` CLI.

claw-installer deploys without cluster-admin, as long as OpenShift lets you create projects or you deploy into a project you already have.
Without a cluster administrator, though, you give up the tighter OAuth setup from <<who-gets-in>>.
And the installer's OpenShell sandbox backend needs an OpenShell gateway that a cluster administrator installed.

== How far along each path is

The raw manifests are the recipe's recommended path.
The recipe tested them with OpenClaw {openclaw-version} on OpenShift 4.22, both as a fresh install and as an upgrade of an older deployment.
The Administrator guide follows them, too.

claw-installer is the alternative the recipe mentions.
The recipe's installer document gives 2026-04-13 as its test date, before the recipe moved to OpenClaw {openclaw-version}, and in several places it no longer matches what the installer's code does.
This guide follows the code at commit {claw-installer-commit-short}.
That code also departs from the recipe's choices in one more way: its health probes request `/` and accept any status below 400.
The recipe's manifests avoid `/` on purpose and probe OpenClaw's health endpoints, because the Control UI answers unknown paths with 200.
xref:admin/deploy-installer.adoc[Deploy with claw-installer] lists every difference that matters.

The sandbox path is the one the recipe's agent description calls a mode for experimentation.
The recipe tested it with OpenShell {openshell-version}.
OpenShell's own upgrades can break existing setups, too: sandboxes created with a 0.0.x release aren't compatible with 0.1.0, so you remove them before the upgrade and recreate them afterward.

== Known limits

The recipe leaves a few things to you.
Most of them concern the two paths that run the gateway as a Deployment, the raw manifests and claw-installer, and each entry says where the paths differ.

Single replica::
The Deployment runs exactly one replica with the Recreate strategy, and claw-installer does the same.
OpenClaw keeps its state in SQLite, which doesn't support concurrent writers, so a second replica isn't an option.
The recipe's own docs state the consequence plainly: there's no high availability.

No NetworkPolicy::
Neither the raw manifests nor claw-installer creates a NetworkPolicy.
What the gateway Pod may connect to, and who may connect to it, is up to your cluster's defaults.
The sandbox is the exception here.
OpenShell creates NetworkPolicies around every sandbox, but they only take effect when your cluster's network plugin enforces them.
On top of that, the sandbox policy blocks all outbound traffic until you allow it.

No read-only root filesystem::
Both containers of the raw manifests drop all Linux capabilities and disallow privilege escalation, but they leave the root filesystem writable.
OpenClaw's own Kubernetes manifests set `readOnlyRootFilesystem: true` and mount an `emptyDir` at `/tmp`, and claw-installer does the same for its gateway container.

Manual token rotation::
Neither the raw manifests nor claw-installer rotates the gateway token for you.
With the raw manifests, it's the value you write into the Secret, and it stays that way until you change it.
claw-installer generates a fresh token each time you deploy from the form, and at no other time.
It also writes the token in plain text into the `openclaw.json` of its ConfigMap `openclaw-config`, so keep in mind who can read ConfigMaps in that project.
