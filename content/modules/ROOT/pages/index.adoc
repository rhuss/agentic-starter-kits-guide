By the end of this guide, you have an OpenClaw agent on Red Hat OpenShift that you chat with in your browser.
It answers with a model you serve yourself through vLLM.
And you deploy it with access to a single namespace, no cluster-admin rights needed.

Why bother running an agent yourself?
An agent that acts for you holds credentials, reads mail, and runs commands on real computers.
So where it runs, and what it may reach, matters more than it does for any app you've installed before.
Running one on your own platform usually means stitching the pieces together yourself.
The {starter-kits-repo}[Agentic Starter Kits] ship a recipe that does the stitching, and this guide walks you through it.

== What the parts are

Three products do the work here.
Let's take them one at a time.

=== OpenClaw

https://github.com/openclaw/openclaw[OpenClaw] is an open-source AI agent.
Instead of you opening an app and clicking through its screens, an agent does the work on your behalf.
OpenClaw keeps its state, memory, and credentials on infrastructure you control, and the model behind it is a plugin you can swap.

At the center of OpenClaw sits the _gateway_: one long-running process that holds the agent's connections and that every client talks to.
In this guide, your client is the _Control UI_, a small web app that the gateway itself serves.
You open it in a browser tab, and that's where you chat with the agent.

=== OpenShell

{openshell-repo}[OpenShell] is an open-source runtime that runs AI agents in isolated sandboxes.
A _sandbox_ is a fenced-off environment for one agent.
Kernel controls decide which files the agent may open and which system calls it may make, and every network connection passes a policy check before it leaves the sandbox.
You declare that policy yourself, and OpenShell enforces it.
The agent never sees real credentials, either: OpenShell adds them only to requests bound for endpoints you approved.

=== vLLM

https://docs.vllm.ai/en/latest/[vLLM] is a library for running large language models and serving them through an OpenAI-compatible API.
The recipe is set up for vLLM, and it accepts KServe or an external API as the model endpoint too.

== How they fit together

image::big-picture.svg["The browser reaches OpenClaw on OpenShift either as a Deployment or inside an OpenShell sandbox whose policy gate controls egress, and both call your model endpoint (vLLM or any OpenAI-compatible API) outside the cluster",role=expand]

You talk to OpenClaw, and OpenClaw talks to your model.
On the main path, the OpenClaw gateway runs as a Deployment with one Pod, and an OpenShift Route carries your browser's HTTPS traffic to it.
Each time the agent needs an answer, the gateway calls your model endpoint over the OpenAI-compatible API.

On the second path, the same OpenClaw runs inside an OpenShell sandbox on the cluster.
`openshell forward start` brings the Control UI's port to your machine.
Here the policy check earns its keep: the sandbox denies all network egress by default.
OpenClaw reaches your model only after you add a policy rule for that endpoint.

Why put these three together?
OpenClaw sends your prompts to the model provider you configure, and in this setup that provider is your own vLLM server rather than an outside service.
OpenClaw can run the agent's commands apart from the gateway in a sandbox of its own, but that sandboxing is off by default, and the recipe's configuration keeps it off.
OpenShell closes that gap from the outside.
It wraps the whole agent in a policy that the kernel enforces on every file access, system call, and network connection.
That's the part I find most convincing: the rules live in code outside the agent, not in a prompt the model is asked to follow.

== Three ways to run it

You can get OpenClaw running in three ways.
Not sure which one fits?
xref:overview/choose-a-path.adoc[Choose how to run OpenClaw] puts them side by side.

Raw manifests::
You apply the recipe's own manifests to your namespace with `oc`.
The recipe recommends this way, and the Administrator guide follows it.

claw-installer::
{claw-installer-repo}[claw-installer] is a web app you start on your own machine.
You fill in a form in the browser, and it deploys OpenClaw for you, with an OpenShift sign-in in front of the gateway.
xref:admin/deploy-installer.adoc[Deploy with claw-installer] covers it.

OpenShell sandbox::
You build an image with OpenClaw inside and run it in an OpenShell sandbox.
Installing OpenShell on the cluster is cluster-admin work, and xref:admin/install-openshell.adoc[Install OpenShell for sandboxes] sets it up.

== Status and limits

[IMPORTANT]
====
The OpenClaw container image is built and published by the OpenClaw upstream community, not by Red Hat.
It hasn't been built, scanned, or validated according to Red Hat standards, so use it at your own discretion.
A Red Hat supported image may follow in a future release.
====

Two more limits might change your decision.
The gateway runs as a single replica, so there's no high availability: its SQLite storage doesn't support concurrent writers.
And the sandbox path is meant for experimentation.
The recipe tested it with OpenShell {openshell-version}.
