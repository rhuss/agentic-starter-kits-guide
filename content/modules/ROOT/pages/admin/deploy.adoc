With the ConfigMap, the Secret, and the storage class prepared, the deployment itself is short.
You create the project with `oc new-project`, create the objects with `oc apply -k`, and then read two logs to see whether the gateway came up with your configuration.
The deployment is done when the Pod shows `1/1 Running` and the gateway log reports `[gateway] ready` along with the model you configured.

Run the commands from `agents/openclaw/deployment/` in your checkout of the Agentic Starter Kits repository, the directory where you edited the files.
If you haven't filled in the endpoint, the model ID, the gateway token, and the storage class yet, do that first in xref:admin/configure-model.adoc[Configure the model endpoint and secrets].
The init container copies the configuration from the ConfigMap only on the first start, so it pays to get it right before you apply anything.

[#first-start]
== What happens during the first start

The base manifests create six objects: the Secret `openclaw-secrets`, the ConfigMap `openclaw-config`, the PersistentVolumeClaim (PVC) `openclaw-state`, the Deployment `openclaw`, the Service `openclaw`, and the Route `openclaw`.
The Deployment's Pod starts two containers in order, and each writes its own log.

First, the init container `init-config` prepares the PVC and logs what it did:

* `Config initialized`: the PVC held no `openclaw.json` yet, so it copied `openclaw.json` from the ConfigMap to `~/.openclaw/openclaw.json`.
* `Config exists, keeping it`: `openclaw.json` was already on the PVC, so it left the file alone.
* `Moved existing state to ~/.openclaw`: on the first start after an upgrade from manifests that kept the state at the root of the PVC, it moved that state into `~/.openclaw`.
Because the moved state includes `openclaw.json`, `Config exists, keeping it` follows.

Once the init container has completed, the container `gateway` starts.
Its startup probe allows 5 minutes, 30 checks 10 seconds apart.
The recipe sized that budget for the `openclaw doctor --fix` pass that runs before the gateway after an upgrade, which xref:admin/maintain.adoc[Back up, upgrade, and remove] covers.
xref:overview/architecture.adoc#inside-the-pod[Inside the Pod] explains why the gateway starts through `args`, what the doctor pass does, and how the three probes work.

== Create the project

None of the base manifests sets a namespace, so they land in the project you name with `-n`.
The example overlay sets the namespace `my-openclaw` in its `kustomization.yaml` instead.
Either way, the project has to exist before you apply.
This guide uses `my-openclaw`, as the recipe does.
If you pick another name, use it in every command on this page and in the `namespace:` field of your overlay.

. Create the project.
+
[source,bash]
----
oc new-project my-openclaw
----

. Confirm that the project exists.
+
Check: `oc` shows the project `my-openclaw`.
+
[source,bash]
----
oc get project my-openclaw
----
// expect: exit 0 and contains "my-openclaw"

== Apply the manifests or your overlay

Apply either the base manifests or your overlay.
An overlay copied from `overlays/example/` builds on the base manifests, so it creates the same six objects with your patches applied.
If `oc` also prints a warning that `commonLabels` is deprecated, that comes from the recipe's base `kustomization.yaml` and doesn't affect the result.

=== With the base manifests

. Apply the manifests to the project.
+
Check: the command succeeds and names the recipe's objects, among them the Secret `openclaw-secrets` and the PVC `openclaw-state`.
+
[source,bash]
----
oc apply -k manifests/ -n my-openclaw
----
// expect: exit 0 and contains "openclaw-secrets" and contains "openclaw-state"

=== With an overlay

. Make sure the overlay's `namespace:` field names the project you created.
+
Check: the field shows `my-openclaw`.
+
[source,bash]
----
grep '^namespace:' overlays/my-env/kustomization.yaml
----
// expect: contains "namespace: my-openclaw"

. Apply the overlay.
It carries the namespace itself, so the command needs no `-n`.
+
Check: the command succeeds and names the recipe's objects, among them the Secret `openclaw-secrets` and the PVC `openclaw-state`.
+
[source,bash]
----
oc apply -k overlays/my-env
----
// expect: exit 0 and contains "openclaw-secrets" and contains "openclaw-state"

[NOTE]
====
For tracing, the recipe copies `overlays/mlflow-tracing/` to `overlays/my-tracing` and applies the copy with `oc apply -k`, but that overlay needs preparation of its own.
Its Pod runs an OpenTelemetry collector sidecar next to the gateway and reports `2/2 Running`.
xref:admin/tracing.adoc[Send traces to MLflow] covers it.
====

== Watch the Pod start

The Pod status tells you whether both containers got through their start.
It doesn't tell you which configuration the gateway runs with.
The two logs do: the init container's log shows whether it seeded `openclaw.json` from your ConfigMap, and the gateway's log names the model the gateway loaded.

. Look at the Pod status.
Repeat the command until the Pod shows `1/1 Running`.
<<first-start>> explains the gateway's startup budget.
+
Check: the `openclaw` Pod shows `1/1 Running`.
+
[source,bash]
----
oc get pods -n my-openclaw
----
// expect: contains "1/1" and contains "Running"

. Read the init container's log.
+
Check: on a new PVC, the log shows `Config initialized`; on a PVC that already held a configuration, it shows `Config exists, keeping it`.
+
[source,bash]
----
oc logs deployment/openclaw -c init-config -n my-openclaw
----
// expect: matches /Config (initialized|exists, keeping it)/
+
`Config exists, keeping it` means that `openclaw.json` was already on the PVC, from an earlier deployment or an earlier start.
ConfigMap edits made since then haven't reached the gateway, and xref:admin/change-config.adoc[Change the configuration of a running gateway] shows how to change the configuration it uses.

. Look for the gateway's startup lines.
The recipe lists these lines as the expected output of `oc logs deployment/openclaw -c gateway -n my-openclaw --tail=20`:
+
[source,text]
----
[gateway] loading configuration…
[gateway] resolving authentication…
[gateway] starting...
[gateway] agent model: vllm/<your-model> (thinking=off, fast=off)
[gateway] http server listening (... plugins; ...s)
[gateway] ready
----
+
The real log holds more lines than these, among them the path of the log file and details about the runtime.
The `http server listening` line names the loaded plugins and the startup time, and the parentheses after the model show its thinking and fast mode settings.
If the doctor pass prints anything, it comes before the gateway's lines, because the entrypoint runs doctor first.
To check the two lines that matter, filter the whole log for them.
+
Check: the output has an `agent model` line with your model reference and the line `[gateway] ready`.
+
[source,bash]
----
oc logs deployment/openclaw -c gateway -n my-openclaw | grep -E "agent model|ready"
----
// expect: contains "agent model:" and contains "[gateway] ready"

. Compare the `agent model` line with your configuration.
The line shows the model reference from `agents.defaults.model` in the `openclaw.json` that the gateway loaded.
With the recipe's configuration, that's `vllm/` followed by the model ID from `/v1/models`, for example `vllm/gpt-oss-120b` for vLLM called directly and `vllm/vllm/gpt-oss-120b` behind OGX.
+
If the line names another model, the gateway runs with a different configuration than you intended.
xref:admin/change-config.adoc[Change the configuration of a running gateway] shows how to correct it in the running gateway.

== If the Pod doesn't become ready

After a crash, the log of the previous gateway container shows what happened:

[source,bash]
----
oc logs deployment/openclaw -c gateway -n my-openclaw --previous
----

When `openclaw doctor --fix` fails, the container exits before the gateway starts, so that log has no `[gateway] loading configuration…` line.
xref:reference/troubleshooting.adoc[Troubleshooting] collects known problems with their fixes, along with further diagnostic commands.

With the gateway ready, continue with xref:admin/access.adoc[Open the Control UI] to reach it from your browser.
